# Synology SPK signing — operator runbook

DSM Package Center verifies SPK packages against a GPG public key it pulls
from the source feed's top-level `keyrings` array. This directory holds the
**public** half of the `kryton-packaging` signing key. The **private** half
lives only in two places: the operator's offline backup, and the GitHub
Actions secret `SYNOLOGY_SIGNING_KEY`.

> **NEVER paste private key material — armored or otherwise — into commits,
> issues, pull requests, Slack/Discord, or any AI chat. Treat the private
> key like a root credential. If you suspect leak, follow the revocation
> procedure below immediately.**

The signing key is **dedicated** to package signing — do **not** reuse it
for git commits, GitHub releases, email, or any other purpose.

---

## Initial key generation

Run on a clean, offline workstation if possible. The key has no expiry by
design (rotation is documented separately) — that means leaks are
catastrophic, so guard the private half accordingly.

1. Create a batch config (not committed; delete after use):

    ```
    # /tmp/kryton-packaging-key.cfg
    %no-protection
    Key-Type: RSA
    Key-Length: 4096
    Subkey-Type: RSA
    Subkey-Length: 4096
    Name-Real: Kryton Packaging
    Name-Email: packaging@<your-domain>
    Expire-Date: 0
    %commit
    ```

    Replace `Name-Email` with a controlled mailbox. `%no-protection` creates
    an unencrypted key — you will set a passphrase in step 3 before export.

2. Generate into a dedicated, isolated gnupg homedir:

    ```
    export GNUPGHOME="$(mktemp -d -t kryton-gpg.XXXXXX)"
    chmod 700 "$GNUPGHOME"
    gpg --batch --gen-key /tmp/kryton-packaging-key.cfg
    shred -u /tmp/kryton-packaging-key.cfg
    gpg --list-secret-keys --keyid-format LONG
    # → note the key id (16-hex), call it $KEY_ID
    ```

3. Apply a strong passphrase to the secret key:

    ```
    gpg --passwd "$KEY_ID"
    # Use a passphrase generated by a password manager; store it in 1Password
    # / Bitwarden / equivalent. The same passphrase goes into the
    # SYNOLOGY_SIGNING_PASSPHRASE Actions secret in step 5.
    ```

4. Export the **public** key to this repo:

    ```
    gpg --armor --export "$KEY_ID" \
      > packaging/synology/keys/kryton.gpg
    git add packaging/synology/keys/kryton.gpg
    git commit -m "feat(nas): add kryton-packaging public key"
    ```

    Phase 1's feed renderer will pick up this file and inject its contents
    into the `keyrings` array in `site/public/synology/index.json` (wired
    in a follow-up; until then operators paste it manually).

5. Export the **private** key into the GitHub Actions secrets — never
   touches disk in plaintext form again:

    ```
    # In the Kryton repo settings → Secrets and variables → Actions → New
    # repository secret:
    #
    #   Name:  SYNOLOGY_SIGNING_KEY
    #   Value: (output of the command below, including BEGIN/END lines)
    gpg --armor --export-secret-keys "$KEY_ID"

    # Second secret:
    #   Name:  SYNOLOGY_SIGNING_PASSPHRASE
    #   Value: (the passphrase you set in step 3)
    ```

    Paste these **directly into the GitHub UI**. Do not save to a file, do
    not echo to your shell history, do not put in a gist.

6. Securely destroy the temporary gnupg homedir:

    ```
    find "$GNUPGHOME" -type f -exec shred -u {} \;
    rm -rf "$GNUPGHOME"
    unset GNUPGHOME
    ```

7. Also generate a revocation certificate now and store it offline (USB
   stick + printed paper, locked away). You will need it if the key is
   compromised:

    ```
    gpg --homedir "$GNUPGHOME" \
        --output kryton-packaging.revoke.asc \
        --gen-revoke "$KEY_ID"
    # Reason: "1 = Key has been compromised"
    # Move kryton-packaging.revoke.asc to offline cold storage.
    ```

## Routine signing (CI)

`build.sh` consumes `GPG_KEY_ID` and `GPG_KEYRING_DIR` environment variables.
The CI workflow imports `SYNOLOGY_SIGNING_KEY` into a temp homedir, configures
`SYNOLOGY_SIGNING_PASSPHRASE` via the `passphrase-fd` mechanism, and runs the
build. After signing, `build.sh` re-verifies the signature against
`package.tgz` before assembling the final SPK — a build that successfully
emits an SPK has by definition produced a valid signature.

## Key rotation

Rotation is intentional, not reactive. Triggers: scheduled annual rotation,
suspected exposure short of full compromise, employee turnover with
plaintext-passphrase access.

1. Generate a new key following "Initial key generation" steps 1-2.
2. Export the new public key into the repo **alongside** the old one:

    ```
    gpg --armor --export "$NEW_KEY_ID" \
      > packaging/synology/keys/kryton.gpg
    git mv packaging/synology/keys/kryton.gpg \
           packaging/synology/keys/kryton-OLD.gpg \
      || true  # if you want to keep both side-by-side
    ```

3. Update the feed renderer to emit **both** keys in `keyrings[]`. DSM
   accepts a signature from either key.
4. Update `SYNOLOGY_SIGNING_KEY` and `SYNOLOGY_SIGNING_PASSPHRASE` to the
   new key/passphrase.
5. Cut **one** release signed by the new key. Verify it installs cleanly
   on a DSM 7.2 VM.
6. In the **next** release, drop the old key from `keyrings[]` and remove
   `kryton-OLD.gpg` from the repo. Existing installs continue to validate
   future updates against the new key.

## Revocation (compromise response)

If the private key leaks, treat it as a security incident.

1. Publish the revocation certificate to a public keyserver:

    ```
    gpg --import kryton-packaging.revoke.asc
    gpg --keyserver hkps://keys.openpgp.org --send-keys "$KEY_ID"
    ```

2. **Immediately** generate a new key following "Initial key generation."
3. Update the feed: replace the compromised key in `keyrings[]` with the
   new one. Do NOT leave the compromised key in `keyrings[]` "for backward
   compat" — that defeats the point.
4. Cut a `vX.Y.Z-pre.N` release signed by the new key.
5. Notify users via the release notes and the install docs at
   `https://kryton.ai/docs/install/synology` — instruct them to remove and
   re-add the package source so DSM re-fetches the keyring.
6. Audit how the leak happened. Write a post-mortem. Rotate any other
   secrets that may have been exposed through the same channel.

## File layout

| Path | Purpose | Committed? |
| --- | --- | --- |
| `packaging/synology/keys/.gitkeep` | placeholder so the dir exists | yes |
| `packaging/synology/keys/kryton.gpg` | ASCII-armored public key | yes (after step 4) |
| `packaging/synology/keys/kryton-OLD.gpg` | previous public key during rotation | yes (transient) |
| `SYNOLOGY_SIGNING_KEY` (GH Actions secret) | ASCII-armored private key | NO — secret only |
| `SYNOLOGY_SIGNING_PASSPHRASE` (GH Actions secret) | passphrase for above | NO — secret only |
| `kryton-packaging.revoke.asc` | revocation certificate | NO — offline cold storage |
