# Docs Site — Implementation Plan

**Spec:** [`../specs/2026-05-20-docs-site-design.md`](../specs/2026-05-20-docs-site-design.md)

Six phases. Phase 1 unblocks everything; 2, 3a, 3b, 4 run in parallel after Phase 1; Phase 5 is a final review pass.

---

## Phase 1 — Scaffold + theming foundation

**Files**
- Create: `kryton/site/package.json`
- Create: `kryton/site/astro.config.mjs`
- Create: `kryton/site/tsconfig.json`
- Create: `kryton/site/.gitignore` (node_modules, dist, .astro)
- Create: `kryton/site/src/content.config.ts`
- Create: `kryton/site/src/styles/tokens.css` (WP oklch palette)
- Create: `kryton/site/src/styles/custom.css` (Starlight variable overrides)
- Create: `kryton/site/public/logo.svg` (copy of `kryton/logos/kryton_logo.svg`)
- Create: `kryton/site/public/favicon.svg` (copy of `kryton/logos/kryton_icon.svg`)
- Create: 3 placeholder pages so the build has something to render:
  - `kryton/site/src/content/docs/index.mdx` (landing)
  - `kryton/site/src/content/docs/start/install/docker.md`
  - `kryton/site/src/content/docs/use/editor.md`

**Steps**
1. From `kryton/site/`, run `npm create astro@latest . -- --template starlight --no-install --no-git --yes`. Edit the generated `package.json` to pin Astro and Starlight to the latest stable. Add `@astrojs/starlight` if not already added.
2. Replace the generated content with the structure above. Delete the Starlight example pages.
3. Configure `astro.config.mjs` with:
   - `site: 'https://azrtydxb.github.io'`
   - `base: '/kryton'`
   - Starlight integration with: title `Kryton`, logo `./public/logo.svg`, favicon `/favicon.svg`, social GitHub link, `customCss: ['./src/styles/tokens.css', './src/styles/custom.css']`, sidebar matching the spec's IA (just the top 3 sections + their first leaf each — fuller sidebar lands in Phases 3a/3b).
4. Populate `tokens.css` by copying the oklch palette from `kryton-wp/theme/kryton/theme.json` → CSS custom properties. Both `:root` (dark default) and `[data-theme="light"]` blocks.
5. In `custom.css`, override Starlight's CSS variables to map to the WP tokens (see spec D4). Set body font to Inter, code font to JetBrains Mono (self-host via `@fontsource/inter` and `@fontsource/jetbrains-mono` — add as deps).
6. `cd kryton/site && npm install && npm run dev` — verify the landing page renders at localhost with the WP look (dark bg, violet accent, Inter body, JetBrains Mono in any code block). Take a screenshot for the user to compare against the WP site visually.
7. `npm run build` — confirm static output to `dist/`, no warnings worse than info-level.

**Gate:** `npm run build` succeeds, dev server visually matches the WP palette (dark bg `oklch(0.18 0.012 280)`, accent violet, Inter + JetBrains Mono).

## Phase 2 — GitHub Pages CI/CD

**Files**
- Create: `kryton/.github/workflows/pages.yml`

**Depends on:** Phase 1 (a buildable site).

**Steps**
1. Write the workflow per the spec's pipeline section. Triggers: push to master under `site/**`, `docs/**`, `packages/server/openapi.json`, `packages/server/src/modules/agents/mcp/tools.ts`, `packages/server/src/plugins/types.ts`, or the workflow file itself; plus `workflow_dispatch`.
2. Two jobs: `build` (checkout + setup-node 24 + `cd site && npm ci && npm run prebuild && npm run build` + upload artifact) and `deploy` (using `actions/deploy-pages@v4`). For Phase 2 the `prebuild` script can be a no-op (`echo "prebuild: nothing yet"`) since the auto-gen pipelines arrive in Phase 3a — wire the real ones there.
3. Add `permissions: pages: write, id-token: write` on the deploy job.
4. Enable Pages on the repo via `gh api -X PUT repos/azrtydxb/kryton/pages -f source.branch=master -f source.path=/ -f build_type=workflow`. If that fails because Pages isn't yet enabled, fall back to `gh api -X POST repos/azrtydxb/kryton/pages -f build_type=workflow` (no source for Actions-based builds).
5. Commit + push the workflow. Watch the run via `gh run watch`. Expected: site live at `https://azrtydxb.github.io/kryton/` within a few minutes.

**Gate:** First Actions run is green and the landing page is reachable at the Pages URL with the WP-themed look.

## Phase 3a — Auto-gen pipelines

**Files**
- Create: `kryton/site/scripts/gen-mcp-tools.mjs`
- Create: `kryton/site/scripts/gen-rest-reference.mjs` (wraps Redocly CLI)
- Create: `kryton/site/scripts/gen-plugin-api.mjs` (wraps TypeDoc, clones kryton-plugins to /tmp)
- Modify: `kryton/site/package.json` — add `prebuild`, `gen:mcp`, `gen:rest`, `gen:plugin-api` scripts; add devDeps `@redocly/cli`, `typedoc`, `typedoc-plugin-markdown`
- Output paths (gitignored): `kryton/site/src/content/docs/advanced/api/mcp-tools.md`, `kryton/site/src/pages/advanced/api/rest.html`, `kryton/site/src/content/docs/advanced/plugins/client-api/**/*.md`, `kryton/site/src/content/docs/advanced/plugins/server-api/**/*.md`

**Depends on:** Phase 1.

**Steps**
1. **`gen-mcp-tools.mjs`** — parse `kryton/packages/server/src/modules/agents/mcp/tools.ts`, extract the `getToolDefinitions()` array (regex or simple TS AST via `@typescript/vfs` is overkill — `acorn` against the transpiled output or even string parsing is fine here since the file is generated/maintained as a flat array literal). Emit a markdown file with a table per tool: name, description, parameters. Render the `kryton/site/src/content/docs/advanced/api/mcp-tools.md` file. Add a "Generated. Do not edit." banner at top.
2. **`gen-rest-reference.mjs`** — `npx @redocly/cli build-docs <path-to-openapi.json> -o ./src/pages/advanced/api/rest.html`. The OpenAPI JSON ships from the server build at `kryton/packages/server/openapi.json`; if not committed, regenerate it as part of `prebuild` via `cd ../packages/server && npm run openapi:dump` (verify that script exists; if not, write one that runs the server in a mode that prints the OpenAPI JSON to stdout). The rendered HTML page is referenced from a Starlight sidebar entry as a "external content" pass-through page.
3. **`gen-plugin-api.mjs`** — clone `https://github.com/azrtydxb/kryton-plugins.git` to `/tmp/kryton-plugins` (depth 1), then run `npx typedoc --plugin typedoc-plugin-markdown --out ./src/content/docs/advanced/plugins/client-api /tmp/kryton-plugins/types/client.d.ts`. Same for the server types: `kryton/packages/server/src/plugins/types.ts` → `./src/content/docs/advanced/plugins/server-api/`. Each generated dir gets a synthetic `index.mdx` that links to the entry types.
4. Wire `prebuild` to run all three generators sequentially. Update Phase 2 workflow if needed so `npm run prebuild` actually does work.
5. `.gitignore` the generated dirs so they don't bloat PRs.
6. Run `npm run prebuild && npm run build` locally. Inspect a sample MCP tool, a sample plugin API page, and the REST reference page to confirm content is real.

**Gate:** All three generators produce non-empty output that links from the Starlight sidebar; `npm run build` succeeds with the generated content included.

## Execution

- **Phase 1** runs first in the main session (Astro scaffolding is sensitive to local Node version + npm cache; subagent friction not worth it).
- **Phase 2, 3a, 3b, 4** dispatched as four parallel subagents once Phase 1's site builds locally. Each has a non-overlapping file scope.
- **Phase 5** runs in main session after all four return.

No commits during Phases 1–4. After Phase 5 lands, a single review pass and the user decides on commits. Pages workflow itself becomes operational only once Phase 2's workflow file is committed and pushed — until then, all of Phases 3a/3b/4's content sits locally.
